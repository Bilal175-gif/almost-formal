## Cross-cutting areas

### Email — entirely absent from the Hono port (highest-impact gap)
- Main `mail.ts` (141 lines) + `email-delivery.ts` (33 lines): **Resend HTTPS transport wins when `RESEND_API_KEY` + `from` are set**; otherwise SMTP via nodemailer (`SMTP_HOST/USER/PASSWORD`, port 587 TLS / 465 SSL, 10 s timeout) — but SMTP is **disabled on Render** (`!process.env.RENDER` guard) because Render Free blocks standard SMTP ports, which is exactly why `email-delivery.ts` exists ("HTTPS works on Render Free, whose standard SMTP ports are blocked"). `from` = `EMAIL_FROM || SMTP_FROM || SMTP_USER`; admin address = `STORE_NOTIFICATION_EMAIL`.
- **When no email key is set:** `transport` is `null`; all three senders (`sendOrderPlaced`, `sendOrderStatus`, `sendContactNotification`) return early silently — **checkout/contact still succeed**, just with no email. `mailStatus()` reports `disabled (Render Free: set RESEND_API_KEY and verified EMAIL_FROM)` or `disabled (configure Resend or SMTP)`. The Hono port reproduces the *silent* outcome by accident (no mail code at all) but **cannot send mail even when `RESEND_API_KEY` is set** — `Env` declares no `RESEND_API_KEY`, `EMAIL_FROM`, or `STORE_NOTIFICATION_EMAIL`, and there is no `mail.ts`/`email-delivery.ts`/`test-mail.ts` equivalent and no `smtp:test` script.
- `sendOrderPlaced` sends **two** mails: customer (items, total, order number, private `accessToken` tracking code, `/order-tracking` link) and admin (customer name/email/phone, total, items). `sendOrderStatus` only for shipped/delivered/cancelled, includes carrier + tracking number. `sendContactNotification` requires `adminEmail` set, sets `replyTo` to the sender.
- Merger must add: a Resend `fetch()` transport (same `https://api.resend.com/emails`, 10 s timeout, `reply_to` mapping), `Env` fields for the key/from/admin address, calls in `POST /api/orders` (after creation only), `PATCH /api/admin/orders/:id/status` (only on real change to shipped/delivered/cancelled), `POST /api/contact`, plus a `mailStatus()`-style startup log. SMTP/nodemailer must **not** be ported (no Node SMTP on Workers; Resend HTTPS is the correct path).

### Public cache — missing
- Main `public-cache.ts`: in-memory cache for `GET /api/products[/:slug]`, `/api/product-filters`, `/api/categories`, `/api/settings` only; TTL from `PUBLIC_CACHE_TTL_SECONDS` clamped 0–60 s (default 0 = off); bounded (≤100 entries, ≤4 MB, ≤256 KB per entry); **any non-GET request clears it immediately and again on finish** (so writes never serve stale catalogue); never caches in-flight reads (generation guard). Checkout always reads stock/prices live from the DB.
- Hono port: **no equivalent** — every catalogue GET hits D1/Prisma. Add a Workers-safe equivalent (per-isolate in-memory map with the same path allowlist, TTL, bounds, and clear-on-write) or accept the extra D1 reads. Note the cache is per-isolate in Workers just as the rate limiter already is.

### Rate limiting — partial, and looser than main
- Main: `express-rate-limit`, global `/api` 180/min **per IP across all paths**, plus per-route 15/min orders, 5/min newsletter/contact, 10/15min login; `standardHeaders: "draft-8"`, no legacy headers.
- Hono: hand-rolled in-memory per-isolate sliding window, same numbers, but the bucket key is **`${path}:${ip}`** — i.e. 180/min **per path per IP**, not 180/min total. An abusive client gets 180/min on every endpoint simultaneously. Also keyed on `cf-connecting-ip || x-forwarded-for || "unknown"` with **no trust-proxy validation** (main sets `trust proxy` only for an explicit `TRUST_PROXY_HOPS` 1–5; Hono trusts any `x-forwarded-for`, which is spoofable). 429 body is a custom JSON message, not the `express-rate-limit` default. Fix: key the global limiter by IP only (and use `cf-connecting-ip` only, dropping raw `x-forwarded-for`), or document reliance on Cloudflare WAF rate limiting as the port's own comments suggest.

### CSRF, cookies, sessions — yes (with the login caveats above)
- `protect` is faithfully ported: `af_session` cookie → sha256 lookup, expiry + `role === "admin"` check, CSRF token `sha256("csrf:"+token)` required on non-GET/HEAD. Session lifetime 8 h in both. Differences are only the cookie attributes in #11 (SameSite None vs Strict, `secure` keyed on `APP_ORIGIN` https vs `NODE_ENV=production`) and the PBKDF2 password issue.

### Admin auth — argon2 vs PBKDF2 (cutover action required)
- Main: `argon2` verify in login; `argon2` hash in `create-admin.ts` (min password 8) and in `start-render.ts` (min **12** for the hosted initial admin).
- Hono: WebCrypto PBKDF2-SHA256, 600k iterations, `$pbkdf2$sha256$<iter>$<salt>$<hash>` format (`auth.ts`); `create-admin.ts` ported to PBKDF2 (min 8). Argon2 hashes are **unverifiable** — login returns `false`, not an error. **Every existing admin password must be reset at cutover** (the port's own comment points at `scripts/admin-reset-d1.mjs`). This is a known, deliberate break, not a bug — but it is a go-live checklist item, and the 401 message will mislead the admin ("Password is incorrect").

### Orders: checkout / cancel / stock restore — partial (logic ported, email missing)
- `createOrder`: same zod `checkoutSchema`, duplicate-product 400, idempotency-key replay with `requestHash` mismatch → 409, COD-enabled gate, archived-product → 409, conditional stock decrement (`stock >= qty`), subtotal + `settings.shipping`, order number `AF-<base36 time>-<hex>`, 32-byte hex `accessToken`, address/items/payment(COD, pending)/shipment rows, `InventoryMovement` −qty "Order placed". Ported to D1 `batch()`: batch 1 decrements (failed decrement → **compensating increments** restore already-decremented items, then 409 naming the product); batch 2 inserts order graph; batch-2 failure → restore stock, re-check idempotency key, replay if the racing checkout won, else 409 "Another order is being processed…". Differences: (a) idempotency pre-read happens **outside** any transaction, so two concurrent identical checkouts can both pass the pre-read (handled by the batch-2 catch + replay, but it is a race window main's `$transaction` did not have); (b) no `onCreated` email callback (see email); (c) no `$transaction` timeouts (`maxWait: 10000, timeout: 15000` — n/a on D1).
- `updateOrderStatus`: same transition table (`pending→confirmed/cancelled`, `confirmed→packed/cancelled`, `packed→shipped/cancelled`, `shipped→delivered`, terminal `delivered/cancelled`), same idempotent same-status return, same "tracking number required before shipping" 400, same claim-then-act pattern (main: `updateMany WHERE status=<old>` inside `$transaction`, comment notes "PostgreSQL permits concurrent transactions: claim this transition before restoring stock…"; Hono: claim `UPDATE … WHERE status=<old>` as batch statement 1, later statements guarded by `EXISTS (order is in the new status)`, claim change-count checked → 409). **Cancel stock restore is ported**: per item `stock += qty` + `InventoryMovement` +qty "Order cancelled"; delivered → payment `collected`, cancelled → payment `cancelled`; audit `order.<status>` row; shipment tracking/carrier update. Differences: no status email (route-level), lost-claim message wording (#21), carrier-nulling quirk (#21).

### Render / Neon Postgres specifics (`db86e99`, `0870d6d`, `9549582`) — Postgres-only, must be adapted or dropped, not ported
- `runtime.ts` `databaseUrl()`: forces `connection_limit=3, pool_timeout=20, connect_timeout=20` onto Postgres URLs (bounded connections for a small Render instance; lets Neon wake up). `db.ts` applies it and passes `datasourceUrl`. **Hono port has no equivalent and needs none** (D1 binding, no connection pool) — but nothing in the port validates that `DATABASE_URL` is absent/unused either.
- `validateHostedEnvironment()` (`0870d6d`): production requires a Postgres `DATABASE_URL` (local SQLite "is not durable on Render Free"), `APP_ORIGIN` must be an exact `https:` origin with no trailing slash, and all three Cloudinary vars must be set — else a `HostedConfigError` with an exact message. `startupErrorMessage()` deliberately **never prints raw provider/Prisma errors** (they can contain URLs/credentials); only the stage + Prisma `P####` code. `initialAdminCredentials()`: `ADMIN_EMAIL` valid + `ADMIN_PASSWORD` 12–256 chars.
- `start-render.ts` (`db86e99`/`0870d6d`): idempotent boot — upsert `storeSettings {id:"store"}`, upsert the 5 seed categories (Regular Ties, Bow Ties, Pocket Squares, Cufflinks, Tie Bars), create initial admin (argon2, min 12) only if no admin exists, delete expired sessions, force `HOST=0.0.0.0` + `STORAGE_MODE=cloudinary`, then load `server.ts`; any failure → sanitised `Render startup failed…` + disconnect + exit 1.
- **Hono port has no `runtime.ts` / `start-render.ts` equivalent at all.** The Worker starts with no env validation, no settings/category seeding, no initial-admin bootstrap, no expired-session cleanup, and no sanitised startup-error path. The merger needs a Worker-appropriate equivalent: validate `Env` (at least `APP_ORIGIN` exact https in production, Cloudinary vars present), seed settings/categories + initial admin (PBKDF2, min 12) via a one-off D1 script or a guarded first-request init — **not** on every request — and keep startup failures free of secrets. `9549582`'s direct-vs-pooled split is Postgres-only: `scripts/migration-database-url.mjs` strips `-pooler` / requires `DIRECT_URL` for migrations because Prisma Migrate needs session-level advisory locks the Neon transaction pooler cannot provide, while the app keeps the pooled URL. On D1 there is no pooler/direct split; migrations go through `wrangler d1 execute` / Prisma migrate against D1 (see `wrangler.toml` comments) — do not port the `-pooler` logic.
- `server.ts`: SQLite-only `PRAGMA journal_mode=WAL` + `busy_timeout=10000` when `DATABASE_URL` starts with `file:`; host `0.0.0.0` on Render else `127.0.0.1`; graceful SIGTERM/SIGINT shutdown. `worker.ts` correctly replaces this with `export default app` — no listen/WAL/signals on Workers. `mailStatus()` is logged at boot in main; the Hono worker logs nothing equivalent.

### Other middleware / hardening gaps in the Hono port
- **No Helmet.** Main sets `helmet()` (security headers) globally; the Hono port sets no security headers at all.
- **No `trust proxy` equivalent** (see rate limiting) — `x-forwarded-for` is trusted raw.
- **No `Cache-Control: private, no-store` on `/api` responses.** Main sets it on every `/api` response; Hono sets `no-store` only on `GET /api/orders/:id` and the admin routes. Public catalogue GETs carry no `Cache-Control`.
- **JSON body limit is header-based only.** Main: `express.json({limit: "100kb"})` enforces on the parsed body. Hono `readJson` rejects only when a `Content-Length` header exceeds 100 KB — a chunked/streamed body without that header bypasses the check. (Counter-note: Hono's malformed-JSON error is a clean 400 "Invalid request body."; Express's parser error falls through to the generic 500 handler.)
- **CORS is narrower and subtly different.** Main: allowlist = `APP_ORIGIN` **+ `ALLOWED_ORIGINS` list** + localhost regex in non-production; allowed responses carry `Allow-Origin/Credentials/Methods/Headers`; OPTIONS → 204 allowed / 403 denied; non-GET with a disallowed origin → 403 "Request origin is not allowed."; `sec-fetch-site: cross-site` without allowance → 403. Hono: only the single `APP_ORIGIN` is ever allowed (no `ALLOWED_ORIGINS` — extra preview/staging origins break); CORS headers are set only on preflight (204) and as an after-`next()` echo of `Allow-Origin` + `Allow-Credentials` (no `Allow-Methods`/`Allow-Headers` on real responses); disallowed OPTIONS → **404 `{"error":"Not found."}`**, not 403; the `sec-fetch-site` check exempts direct Worker calls from the web app itself (deliberate, documented). Also Hono's `Access-Control-Max-Age: 600` on preflight has no Express counterpart (harmless).
- **No `PUBLIC_CACHE_TTL_SECONDS` handling** (see public cache).
- **No `mailStatus` / startup email log, no `test-mail` script.**
- **`HttpError` status type is a narrow union** (`400 | 401 | 404 | 409 | 413 | 503`) in Hono `orders.ts` — fine for current uses, but a future 403/500 from shared code would be a type error rather than a runtime one.

## Porting checklist (to reach main parity)

Excluding Postgres-only items (pool params, `DATABASE_URL` validation, direct-vs-pooled migration URLs, WAL pragmas, SIGTERM handling) and excluding R2 (to be replaced by Cloudinary).

1. **Email (biggest gap):** add a Resend `fetch()` transport (`email-delivery.ts` equivalent, `https://api.resend.com/emails`, 10 s timeout, `reply_to` mapping); add `RESEND_API_KEY`, `EMAIL_FROM`, `STORE_NOTIFICATION_EMAIL` to `Env`; implement `mail.ts` equivalents — `sendOrderPlaced` (customer + admin), `sendOrderStatus` (shipped/delivered/cancelled only), `sendContactNotification` (`replyTo`, requires admin address); call them from `POST /api/orders` (after creation only), `PATCH /api/admin/orders/:id/status` (only when the status actually changed to shipped/delivered/cancelled), and `POST /api/contact`; keep the no-key behaviour silent (no email, no failure) and log a `mailStatus()`-style line at boot. Do not port SMTP/nodemailer.
2. **Add `GET /api/product-filters`** (distinct categories/patterns/colors/conditions + `maxPrice` over non-archived products) — the only wholly missing route; the storefront filter UI depends on it.
3. **Fix health:** return `{ ok: true, service: "almost-formal-api" }` so the keep-alive contract holds (or delete/retarget the keep-alive workflow — the rework has no workflows at all).
4. **Fix `imageUrls` validation:** accept Cloudinary URLs (`https://res.cloudinary.com/<cloud>/image/upload/…`) in `productSchema` on POST/PATCH product, exactly as main's `isCloudinaryProductUrl` refine does; otherwise no Cloudinary-backed product can be created or edited.
5. **Cloudinary uploads (replacing R2):** implement signed-`fetch` Cloudinary upload (no Sharp on Workers — resize client-side before upload or use Cloudinary delivery transformations); enforce the 5 MB + JPEG/PNG/WebP rules and validate the real content type, not just the client MIME; return the `secure_url`; preserve the 503-when-unconfigured behaviour (missing/incomplete Cloudinary creds); add orphan-image cleanup on product PATCH/DELETE (delete a Cloudinary URL only when no product image or order item still references it).
6. **Add the `inStock` filter** to `GET /api/products` (`stock > 0` when `inStock=true`).
7. **Admin password cutover:** reset every existing admin password to a PBKDF2 hash before go-live (argon2 hashes can never verify); document it, and consider a clearer 401 message for legacy-hash accounts instead of "Password is incorrect."
8. **Port the `adbfb94` web fallback** in `admin.tsx`: on DELETE 409, auto-archive via `PATCH {archived: true}` with the "Removed from shop. Order history is preserved." notice, plus the "Show archived products" toggle. (API rule already exists.)
9. **Add a public-cache equivalent** for the catalogue GETs (allowlist `/api/products[/:slug]`, `/api/product-filters`, `/api/categories`, `/api/settings`; TTL from `PUBLIC_CACHE_TTL_SECONDS` clamped 0–60; ≤100 entries / ≤4 MB / ≤256 KB each; clear on any non-GET, including failed writes) or explicitly accept uncached D1 reads.
10. **Fix rate limiting:** make the global limiter per-IP (not per-path-per-IP); key on `cf-connecting-ip` only — never trust raw `x-forwarded-for`; restore standard rate-limit headers. Alternatively document Cloudflare WAF rate limiting as the production control.
11. **Restore hardening headers:** Helmet-equivalent security headers on all responses; `Cache-Control: private, no-store` on `/api` responses (at minimum the admin/auth/order ones already covered); enforce the 100 KB JSON body limit on the parsed body, not just the `Content-Length` header.
12. **Restore CORS parity:** support an `ALLOWED_ORIGINS` list in addition to `APP_ORIGIN`; return 403 (not 404) for disallowed preflights; send `Allow-Methods`/`Allow-Headers` on real responses, not only preflights. Decide deliberately whether the SameSite=None-when-https cookie change stays.
13. **Startup/seed equivalent:** validate `Env` at boot (exact-https `APP_ORIGIN` in production; Cloudinary vars present); one-off seed of `storeSettings {id:"store"}` + the 5 categories + initial admin (PBKDF2, min 12 chars) + expired-session cleanup — via a deploy script or guarded first-run init, never per-request; keep startup errors free of secrets (stage + error code only, as `startupErrorMessage` does).
14. **Error mapping for D1 writes:** map raw D1 batch failures to the same statuses Express returns — duplicate slug/sku/email → 409, missing row → 404 — instead of leaking everything as 500. Also fix the carrier-nulling quirk (don't overwrite `carrier` with NULL when only `trackingNumber` is supplied) and align the lost-claim 409 message with main ("Order status changed. Refresh and retry.").
15. **Verify D1 FK cascades:** confirm `ON DELETE CASCADE` is enforced for `ProductImage`/`ProductCategory` on D1 before relying on raw `DELETE FROM "Product"` in the product-delete path; if not enforced, delete the child rows explicitly in the batch.
16. **Port the web cold-start guards** (`lib/api.ts`): non-JSON response rejection (gateway HTML → "temporarily unavailable", 502), `ApiError` with status, read-retry with backoff (5xx only, never 429, never writes). The Render keep-alive job itself is unnecessary on Workers — delete it rather than leaving it pointed at Render — but keep the `service` field in health (#3) so any health consumer keeps working.
17. **Housekeeping:** add `GET /api/admin/uploads` protection check (already protected via `/api/admin/*` — verify the mount matches the bare `/api/admin` prefix the same way Express does); re-add a `test-mail`-style script for the Resend path; note the per-isolate rate-limit/cache limits in deploy docs.
